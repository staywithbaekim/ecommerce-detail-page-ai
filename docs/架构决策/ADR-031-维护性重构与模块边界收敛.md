# ADR-031：维护性重构与模块边界收敛

## 状态

已批准实施（2026-09-17），分阶段实施至 B-22（2026-09-18），整体未关闭。本 ADR 只批准分阶段重构路线和边界；每个具体抽取仍需通过对应任务书的验证门。

B-21 清理证据见 [兼容转发清理与重启验证](../验证/ARCH-01-B21兼容转发清理与重启验证-20260918.md)：331 个属性/命令别名、53 个方法转发及宽泛通知桥已移除；页面直接观察协调器，密码输入清空由设置控件拥有。Shell 560 行、业务服务接口字段 0；B-21 生产代码净减 1,003 行，旧数据读取与两次正常重启通过。窄 host 和仍有业务调用的用例门面是正式边界，不因存在委托而删除。

B-22 补充：[后台进程中断与恢复状态验证](../验证/ARCH-01-B22后台进程中断与恢复状态验证-20260918.md)已完成受控 provider 边界下的进程退出与两次重新恢复。发现并单独修正原有的恢复后仍显示“分析中”问题：scheduler 仅输出不可变的未决恢复事实，由命令快照传给投影；不增加持久化字段，不改变账本/排队/重发或既有外部合同。四组回归 704 通过。SIZE-S7/RENDER-01 正式联验收仍未关闭，B-21 正常原生窗口证据与 B-22 进程探针证据不可混称。下方记录保留为历史阶段状态。

## 背景

项目已经采用 Application 依赖 Domain/Contracts、Infrastructure 实现 Application ports 的分层方向，并冻结了 renderer-neutral `RenderPlan`、AI 结果合同、SQLite checkpoint 和 Photoshop/UXP bridge 边界。近期模板无限画布、参考学习、AI 颜色版本规划和尺码表功能连续接入，代码主要通过追加字段、可选依赖和兼容分支扩展。

这使代码量持续增长，但问题不是底层架构缺失，而是表现层和 Application 编排热点没有随着功能边界一起拆开。详细数据和文件清单见 [维护性架构审计](../技术方案/维护性架构审计-2026-09-17.md)。

## 决策

采用分阶段的抽取式重构：先保持现有合同和行为不变，再从 Application 热点抽取职责，随后拆分页面 ViewModel 和 WPF 控件，最后删除已经没有调用者的兼容路径。旧入口在证据不足时保留，但必须登记退出条件。

核心顺序固定为：

1. 冻结行为与测试基线。
2. 拆分 `AiBatchAnalysisWorkflow` 的命令、投影、恢复和渲染准备职责。
3. 将 `MainWindowViewModel` 降为导航和生命周期 Shell，页面各自持有状态。
4. 将 `MainWindow.xaml` 拆成页面控件和局部弹层。
5. 在真实验收、重启和旧数据兼容验证完成后删除旧路径。

## 不变的架构边界

- `Domain` 不依赖 WPF、SQLite、HTTP、Photoshop 或供应商 SDK。
- `Application` 只通过端口和领域模型编排用例，不引用 `Infrastructure` 或 WPF 类型。
- AI 和产品规则不进入 Photoshop/UXP 执行适配器。
- `RenderPlan`、AI 结果合同、SQLite migration、checkpoint、manifest 和 bridge 协议在本重构中保持兼容。
- 源 PSD、源照片、市场尺码图和正式输出的只读/原子性安全边界不降低。

## 代码治理规则

- 新页面功能不得继续把业务字段、异步用例或持久化转换加入 `MainWindowViewModel`。
- 新 AI 行为不得继续把投影转换、恢复逻辑或尺码/渲染准备加入同一个工作流类。
- 每次抽取必须有旧门面或适配器作为短期过渡，并在任务书中写明删除条件。
- 抽取提交与行为变更提交分开；删除兼容路径单独提交。
- 行数只作为趋势信号，不能用删除验证和安全门来换取“代码变少”。

## 退出条件

本 ADR 只有在以下证据齐全后才可标记为已实施：

- 受影响 Application、Infrastructure、WPF UI 和架构测试通过。
- 现有 AI、模板、尺码表、RenderPlan 和恢复验收没有行为回归。
- 每个已删除兼容入口都有调用方搜索、旧数据读取和重启证据。
- 主窗口和 AI 工作流的职责、依赖数量和文件规模已按审计表重新统计，并且新增功能不再回流到热点文件。
