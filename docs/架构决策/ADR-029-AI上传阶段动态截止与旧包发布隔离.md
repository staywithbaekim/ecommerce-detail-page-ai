# ADR-029：AI 上传阶段截止修正与旧运行包隔离

## 状态

已批准并实现（2026-09-13）。本 ADR 补充并更新 ADR-028 的上传阶段参数；历史请求、账单、
缓存和失败批次不回写、不重放。

## 问题证据

产品负责人看到的“提交失败，可安全重试”来自仍在运行的旧包
`tmp/tpl-learn-20260912-adr028-v4-debug-app/Desktop.App.exe`。该包的脱敏传输日志记录：

- 北京时间 2026-09-12 22:07:39 开始构造 `8,401,443` bytes 的 24 图目标请求；
- 两次尝试都在上传阶段约 45 秒无进度，`upload_bytes_written=0`、
  `upload_completed=false`；
- 没有 HTTP 状态、响应头、供应商 request reference；终态为
  `AI_PROVIDER_SUBMISSION_TIMEOUT`；
- 火山控制台没有对应账单，因此不能解释为“火山推理超过 180 秒”。

这一步失败在本机请求体写入传输通道之前/期间，UI 的“检查网络”是该错误分类的动作提示；
它不是模型规则、凭据、响应 Schema 或 PSD 图层解析失败。旧包的二次自动尝试同样使用旧的
180/45 参数，所以最终页面显示“提交失败，可安全重试”。

## 决策

### 1. 新请求的分阶段截止

| 阶段 | 当前默认上限 | 说明 |
| --- | ---: | --- |
| 总请求墙钟 | 300 秒 | 覆盖上传、响应头和响应体 |
| 上传绝对上限 | **240 秒** | 适配已观测的慢上行；仍受 300 秒总墙钟约束 |
| 上传无进度上限 | **90 秒** | 允许慢连接在大块写入之间恢复；仍受 240 秒上传上限约束 |
| 上传完成后响应头 | 120 秒 | 只在请求体已完整写入后开始计时 |
| 响应体 | 60 秒 | 收到响应头后读取完整结构化响应 |

`HttpClient.Timeout` 继续为无限，唯一的前台硬截止由适配器的单调时钟 scope 执行。上传
未完成的超时/网络错误是可安全重试的“未送达”；上传完成后响应头或响应体失败仍是
`AiResultUnknown`，禁止自动重发。

### 2. 上传实现细节

- 请求仍使用 HTTP/1.1 语义，但 `RequestVersionPolicy` 改为 `RequestVersionOrLower`，允许
  正常回退，避免固定版本协商增加无效等待；
- 显式关闭 `Expect: 100-continue`，避免延迟握手占用上传窗口；
- 请求体按 64 KiB 写入并记录进度，不改变 payload 字节、图片内容、源文件或供应商合同；
- 适配器在 HTTP 前继续执行最终 UTF-8 JSON 的 16 MiB 本地预算、40/24 张数量门和所有
  引用/Schema/授权/费用安全门。

### 3. 发布隔离

旧包不会被覆盖。包含本修正的 Debug 包为：

`tmp/tpl-learn-20260913-transport-fix-debug-app/Desktop.App.exe`

该包含已验证的 `psd-inspection-worker`。使用时必须先关闭旧 `Desktop.App`，并建立全新
批次；旧失败批次不得复用。隔离验收优先通过全新 `--data-root=<目录>` 运行，继续使用默认
数据根时也只能复用已提交模板，不能继续旧失败批次。

## 验证

- `VolcArkAiAdapterTests` 与 `AiAnalysisV4TransportBudgetTests`：67 通过、3 跳过、0 失败；
- 新包 Debug publish：0 警告、0 错误，worker SHA-256 保持已验证值
  `778E44E2BEB3CA8DFD73912635F0D60D0B4E06839B1953C1AC4F443C6BEE1DCE`；
- 2026-09-13 01:27（北京时间）使用同一 24 张“简唏7707-75”照片、11 条动态规则和当前
  正式 adapter 只发起一次真实请求：最终 JSON `8,401,443` bytes，129 个 64 KiB 级进度点，
  `8,401,443/8,401,443` bytes 在 `184,899 ms` 完成上传；`205,409 ms` 收到 HTTP 200，
  `205,414 ms` 完成 `8,268` bytes 响应体读取。结果为 `Completed`，请求数 1、无重试、
  usage=`33,568/972/34,540`，没有 180 unknown、引用不闭合或提交超时。该次真实证据直接
  证明旧 180 秒上传上限不足，而 240/90 秒与 64 KiB 分块在本机当前慢上行下可以闭合；
- 本 ADR 原始回归时，WPF 聚合测试曾在测试宿主加载资源包时触发
  `Application.GetResourcePackage` FailFast；它与产品运行时及传输实现分离。2026-09-13 已移除逐用例
  Application/Dispatcher 关闭和 WPF 私有字段反射重置，改为共享 STA/Application 宿主；WPF 36/36
  多轮及完整 solution 聚合 648 通过、5 跳过、0 失败。修复记录见
  `docs/验证/WPF-UI-20260913-测试宿主生命周期隔离修复记录.md`。

## 与既有记录的关系

- ADR-028 仍保留 2026-09-12 的 40/24 图、V4、16 MiB 和 300 秒总墙钟决策；其上传阶段数值
  由本 ADR 更新为 240/90；
- ADR-026/027 中的 180 秒失败日志和 V3 成功日志是历史证据，不改写；
- PRD 的 300 秒整批 `machine_total` 与本 ADR 的单请求 300 秒墙钟不是同一验收项。
