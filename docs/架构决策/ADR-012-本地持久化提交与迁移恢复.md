# ADR-012：本地持久化、提交与迁移恢复

## 状态

已批准并冻结数据边界和恢复协议；实际实现、文件系统差异和故障注入由 `DATA-01` 验收。

## 日期

2026-08-27

## 背景

长批次必须在应用关闭、Photoshop 异常、外置盘断开、复制中断或进程崩溃后继续。SQLite 记录、输出文件和检查点存在双提交问题，不能只依赖数据库的一行状态，也不能把源 PSD、源图或正式输出当作应用临时文件处理。

## 决策

1. 本地结构化数据使用 SQLite，启用 WAL；数据库由单实例、单 writer 负责写入，UI 不直接访问数据库。
2. 模板、批次、任务和每页输出各自拥有 `manifest.json`；页面恢复依据 `manifest + checkpoint + 文件 hash + commit marker` 四方一致性。
3. 所有 JSON/manifest/checkpoint 采用临时文件写入、flush、长度/hash 读回、原子替换；SQLite 状态在同一业务提交阶段推进，不使用“先改数据库、再猜文件是否成功”的单向流程。
4. 正式输出在目标输出卷的 `.app-staging/<batch>/<page>/<attempt>` 中准备，逐个校验后按目标清单提交；页级 marker 最后写入。替换已有目标时保留短期 journal/备份，失败或崩溃恢复旧文件或进入 `RecoveryRequired`。
5. 跨卷迁移使用 `migration.journal` 和 `ready.marker`。复制、校验、数据库提交、根指针切换和旧位置清理必须可单独恢复；旧位置在新位置完成前保持可用。
6. 单实例通过用户范围互斥锁和激活现有窗口实现。第二实例不得绕过 SQLite writer、迁移锁、输出锁或 Photoshop 单通道。
7. 删除任务、模板、缓存和卸载只处理应用自有对象；原始 PSD、源图、市场尺码图、人工结果和正式输出永不由应用自动删除。
8. AI 分析采用批次全量、单调版本的业务 checkpoint：先 stage `ai-analysis-state/v1` manifest；再用一个 SQLite transaction CAS 写入 manifest 声明的全部 request/session 及可选 usage/cache graph，并落 durable `Pending` journal；随后原子切换 `committed.marker`；最后按 checkpoint ID、stage token、manifest/payload digest 将 journal CAS 收口为 `Committed`。usage 可无 cache，cache 存在时必须闭合 usage、result reference、model config 和时间；失败、取消、未知结果或无可用计量时二者均可为空。
9. AI 新 checkpoint 的 UTC `CreatedAt` 必须严格晚于同批次最新 committed 版本，并保留上一版本的全部历史 request/session graph；即使 payload 相同，expected request status、session status 和 selection revision 仍必须匹配。AI-S3 的 cache 失效采用 checkpoint 内逻辑 tombstone：保留原 cache key、usage、result reference 和历史 manifest 引用，只把 `IsReusable` 单向改为 `false`；同 fingerprint 此后 fail closed，不复活旧 key，只有正式分析输入或配置变化形成新 fingerprint 才能建立新 graph。物理清理仍须在核对所有活动/恢复引用后另行执行，不能借新 checkpoint 静默丢弃。开始新 stage 前必须双向验证最新 committed journal、committed manifest 和完整 graph；任一侧缺失、摘要不符或 graph 损坏均进入 `RecoveryRequired`，不得以新提交覆盖损坏证据。

## 恢复状态

### 2026-09-25 D7首次按款发布与回源输出决策（分批实现）

用户新增“各款源目录”可选模式，与“统一目录下按款输出”并列。新批次需显式确认模式；统一模式保存用户选择的公开根，回源模式不保存或猜测一个公共目标根。实际款目录始终由已提交输入清单的InputRoot与StyleId对应SourceDirectoryRelativePath解析；单款空相对目录就是用户精确选择的目录，不上溯父款号。

内部页级artifact证据与用户公开目录分离：现有OutputRoot继续表示已登记页证据根，不把旧output_root改成源目录，不改旧manifest/checkpoint或执行身份。新增可选OutputSelection作为新批次的公开输出意图；null仅表示历史发布布局。先在SQLite新增附属选择表，与输入graph同一事务保存；输入commit journal v2携带相同选择并核对，v1保持原字节/读取语义。创建、重配草稿、扫描提交和缺库恢复均不得丢失选择；扫描开始后不能改变意图。旧迁移不改，旧二进制拒绝新schema。该持久化切片完成前后均不擅自启用未接完的UI；非null意图在公开发布器接好前拒绝进入旧渲染入口，不能默默降回历史布局。

后续公开发布采用每款独立、同目标卷的受控stage，先登记不可变的batch/style/源目录/目标目录及页面集合。所有选定可生成页已核验，且没有Unknown/运行中/未决提交，才以一次不覆盖目录rename公开该款完整集合。JPG与可选PSD由同一款目录原子发布；清单、marker、源页checkpoint及长度/hash可交叉恢复，数据库落后时只收口同身份提交，不再次渲染。不把多文件逐个rename或无登记复制当原子提交。公开目标一旦存在，非本次已登记且完整核验的目录都按冲突处理，提示用户重新选择；不自动加随机后缀、合并或覆盖。回源默认子目录为“生成详情页”，源目录本身永不作为可替换单元。

扫描排除以本机持久化发布/暂存归属与目录身份校验为依据，不按“生成详情页”这个通用名字排除用户素材，也不相信单个可伪造marker。无归属、重解析或身份不符的路径不自动回收/排除。每款目标可写性/冲突必须在派发前检查，跨卷仅复制已核验页到目标卷stage再发布。结果读取/打开目录、发布失败状态与恢复需一起接入，随后真实多款验证才关闭D7；本段为决策，不宣称发布器或回源功能已实现。

2026-09-25续接实现细化：公开目标登记追加SQLite v20附属表，不改v1～v19。先在一个writer事务冻结整批目标、输入manifest摘要、初始render journal页集合（含阻断占位）、各源及目标父目录身份；再逐款以Windows原生相对父句柄的排他FILE_CREATE创建同卷stage，并在仍持有创建句柄时登记其真实目录身份。不能用CreateDirectory成功后重新按路径打开来猜归属。创建与SQLite登记之间崩溃遗留为未登记冲突，保留现场，不以名字/marker自动认领或清理。已登记stage只按同输入/计划/源/父/目录身份恢复；本子门只证明目标冻结与目录创建/归属，不证明JPG核验、整款rename或完整磁盘可写性。首次公开提交/扫描排除/UI仍须后续接通，入口gate保持。

2026-09-25整款提交继续细化：追加v21公开manifest状态与逐文件归属两附属表，Copying→Verified→Committed单向推进；输入/页级账本和v1～v20不改。先核对当前journal全部无Unknown/Running/Submitting，各款所有原始可生成页均Committed且manifest/checkpoint/marker/hash闭合；公开集合只含该冻结款的原始可生成页。stage每个媒体/公开manifest/marker先排他创建并登记卷号/file ID/创建时间，再写内容；写入完成后登记Verified，恢复只允许同identity、尚未Verified的未公开文件重写，已Verified或公开成品永不改写。创建和归属落库间失败留下未知文件冲突，不凭同名/hash认领。源/父/stage持有身份句柄，公开rename通过目录原句柄、不覆盖已存在目标；Verified库落后且目录已改名时，只读核验同目录/每文件identity和完整内容后收口Committed，不渲染、不复制另一套目标。此实现未通过聚焦恢复测试且UI/扫描排除未接前，正式factory安全gate继续保持。

2026-09-25安装态回源实测补充：新私有证据根首次写入后，宿主的合并LocalAppData视图可让既有`render`仍解析到原目录、新`publication-evidence`子目录解析到包的`LocalCache/Local`；只检查“当前父句柄路径+叶名”不足以接受这个真实OS映射。仅内部证据只读租约可显式允许：从已打开OS句柄取得实际路径，要求同用户LocalAppData/Packages/单一包目录/LocalCache/Local/完全相同相对后缀，拒绝Packages嵌套及其他根/后缀；保持全部逻辑和物理祖先无重解析、8.3拒绝、拒删除共享，物理叶再次按句柄核对身份。该例外不授予创建/rename权限，不用于用户源或目标目录，不改Bridge资源规则/持久化身份/manifest。真实失败、映射证据及聚焦负例留在D7源目录实机报告；七页已Committed时只恢复公开提交，不渲染。

### 2026-09-24 尺码内容修复登记（R1代码已实现，真实改值门待验）

尺码修复不得先覆盖生成前的`current.json`再尝试重生成。采用journal v3追加页的类型化修复origin，绑定请求身份/摘要、期望父journal/attempt/基plan及基/新尺码不可变快照JSON。快照严格结构、大小和领域data digest校验，并与对应冻结plan逐格闭合；之后编辑由选中逻辑页最新修复祖先取基线，生成前current文件继续只服务未冻结计划。小型结构化尺码数据可保存在既有SQLite journal，避免再引入文件修订指针与数据库双提交真相；PNG仍在应用自有resources中按内容身份独立落盘/读回，未有成功登记的候选无执行权限。

v18只新增修复请求索引，batch/request唯一，并绑定page index、birth revision、request digest；复用v17的出生origin表。请求索引、v3新attempt、`RenderPageRepairRequested`事件及任务重开同一writer/事务/CAS，重试同请求返回同一个attempt，内容不同或陈旧基线拒绝。恢复核对索引、父/出生revision、严格plan差异白名单和任务事件；原计划重生成仍严格PreservesFacts。单页范围、Unknown不重投、逻辑页输出计数和历史问题保留。

旧v1/v2、旧migration/checksum、输出manifest/checkpoint字节不回写；v3不可降回v2，旧二进制因新迁移拒绝数据库。R1仍采用独立artifact提交保留旧图，**并非PRD16.4同页替换完成**；R2必须另有可恢复发布协议，不把artifact提交改成无记录覆盖。

生产修复使用`ISizeTableRepairAdmission`租约：由既有AI workflow gate隔离新分析/选图/准备命令，核对admission、consumer、copy preparation、持久化历史请求和恢复状态，无未决才进入修复候选准备/SQLite登记；空或缺失记录不证明安全，不发起新AI。租约不构成第二任务调度器。正式v17→v18及只读编辑入口已实测，业务历史与保护文件不变；尚未实际改值执行，详见 [R1记录](../验证/REPAIR-01-R1尺码修复实现与只读实机入口-20260924.md)。

### 2026-09-21 RENDER 私有暂存归属恢复

基础设施增加 `render/temporary-files/<plan-digest>.json`，不改变SQLite、RenderPlan、执行journal或正式manifest格式。记录仅包含计划身份、受控暂存相对路径和Windows卷/文件编号/创建时间；媒体写入和提交前flush归属记录。恢复须先验证同计划执行终态，完成页还须核对manifest/checkpoint/hash/marker；未知执行或无归属的旧记录不自动回收。删除通过拒重解析且核对文件身份的独占删除句柄完成，不枚举删除目录、不删除正式输出或源文件；被替换/硬链接/在用文件保留。缺失文件允许重复清理，完成标记防止再次清理新同名对象。进程在创建文件但归属尚未落盘、或准备中断且无法证明未派发的极早窗口保留现场，不声称完全无残留。限定实机证据见 [稳定性与收口](../验证/RENDER-01-S6-S7稳定性与产品收口-20260921.md)。

### 2026-09-21 单页追加 attempt 与任务终态重开

SQLite v17 只追加 `render_batch_attempt_origins`，以批次/页索引记录新 attempt 的出生 revision 和任务事件 ID；旧 migration/checksum、journal、checkpoint、manifest 和正式输出不改。只有用户明确选择的已确认 Committed/Failed/Cancelled 逻辑页可以追加 max(attempt)+1；任一未知/执行中页、陈旧 attempt 或正在运行的编排器均拒绝。新账本 Version=2，`RegenerationPageIndex` 固定为此次追加的唯一页，恢复及后续执行不投递取消批次原有的 Planned 页。没有追加的历史账本继续 Version=1。

新 revision、origin、`RenderPageRegenerationRequested` 事件与任务投影在一个 SQLite writer/事务中提交。事件仅将合法终态或安全暂停/待处理状态重开为 ReadyToRender，绑定逻辑页键及新计划 digest；原输出计数、已提交页集合及历史问题事件保留。通用任务写口不能单独生成此事件。任何写入失败整体回滚，进程在提交后退出则从唯一新 attempt 恢复。历史问题计数保守保留，不把成功重生成描述为抹除全部历史问题。

读取 Version=2 须核对首版、全部追加页的 origin/出生版/父版 SHA-256、严格结构、同一页不可变准备事实和对应任务事件；缺失或损坏阻断恢复。出生版按索引查找，避免扫描所有进度 revision。仅更新内存读取投影，不回写旧 payload。新迁移使旧二进制拒绝该数据库，不承诺降级可写。正式输出仍由现有四方一致与单页原子提交核验，重生成的独立 artifact 目录不覆盖旧输出。实际证据单独记录，代码和测试不关闭 S6。

### 2026-09-20 批次 intent 与准备事实恢复

SQLite v16 追加 `render_batch_journals`，以 batch/revision 为主键保存带 SHA-256 的严格 JSON。提交前先写 Submitting；失去响应、账本提交或输出证据时保留 Unknown/RecoveryRequired，不重投。历史页 plan、变体、attempt、已确认执行 ID 和 commit 不可覆盖；终态重生成仍须另行定义追加 attempt/任务事件兼容。

页新增可选 `PreparationReasonCode`/`OutputVariantName`，准备事实与执行结果分别保存且不可变。旧 v16 payload 读取须验证 revision 1 的 hash/结构和同页原计划身份，从初始 ReasonCode 形成只读准备投影；没有名称不猜颜色。缺失/损坏首版阻断恢复，不用“已提交”推断视觉检查通过。旧 payload/checksum、RenderPlan、manifest、migration 不改，后续 revision 可保存明确补回的原因。旧二进制严格 JSON 不支持新字段，不声明降级可写兼容。

正式结果读取须 manifest/marker/文件 hash/DB Committed 一致，预览口仅持拒写删的只读 JPG 句柄，不执行恢复提交或修改输出。限定实机证据见 [批次编排与桌面恢复](../验证/RENDER-01-S6批次编排与桌面恢复验证-20260920.md)。

### 2026-09-20 RENDER 变体与 attempt 兼容

SQLite v15 新增 `render_page_checkpoints`，主键为 `(task_id, style_id, page_id, output_variant_id, attempt)`，plan_digest 唯一；无变体以空串存储、应用投影为 null。迁移仅复制旧 checkpoints 中 render_output 行，原表/原行、已有 migration/checksum 和 manifest 字节不改。旧 manifest 序列化不补 null 字段。渲染 manifest 与 checkpoint 仍在同一业务事务推进；通用 checkpoint 写口不能替代正式提交。不同变体各计一页，同一变体新的 attempt 保留历史而不重复增加 output_count。

真实 v14 普通页 run 的受控副本已迁移 v15 并通过新进程四方一致恢复，output_count=1、不重渲染、JPG/PSD/manifest hash 不变；原数据库及旧正式输出未修改。多颜色、重生成和恢复计数已有存储测试，真实批次证据仍待完成。

| 发现 | 处理 | 结果 |
| --- | --- | --- |
| `copying` 且无 `ready.marker` | 删除或隔离新位置临时目录 | 继续旧位置 |
| hash 校验失败 | 隔离新位置并记录首个不符项 | 继续旧位置，可重试 |
| ready 存在但指针仍旧 | 校验 manifest 后由用户选择切换或清理 | 默认不自动切换 |
| 指针已切换但 DB 未完成 | 依据 journal 恢复事务；不完整则回退 | 不留下半迁移状态 |
| DB 已提交但文件 commit 未确认 | 以 marker/hash 重建或标为 `RecoveryRequired` | 不重复覆盖未知目标 |
| AI DB `Pending` + staged manifest | 依据同一 checkpoint/stage token/digest 校验完整 graph 后继续 marker commit | 不盲目重发 AI、不覆盖较新版本 |
| AI DB `Pending` + committed manifest | 校验 marker、manifest 和完整 graph 后只收口 journal | 不重复写业务图 |
| AI staged manifest 无 DB journal | 只回滚匹配 token/digest 的应用自有 stage | 保留既有 committed 版本 |
| AI committed journal/manifest 任一缺失或不匹配 | 阻断新 checkpoint 并标记 `RecoveryRequired` | 保留 marker/journal 供诊断，不猜成功 |
| 外置盘不可达 | 暂停新工作，保留记录和 checkpoint | 重新连接后继续 |

## 候选与取舍

| 方案 | 优点 | 风险 | 结论 |
| --- | --- | --- | --- |
| SQLite WAL + manifest/journal | 事务查询成熟，大文件不塞进 DB，恢复证据清晰 | 需要处理 DB/文件双提交 | **采用** |
| JSON-only | 文件直观 | 并发、索引、崩溃一致性和单 writer 难保障 | 不采用 |
| 嵌入式其他数据库 | 可能减少部分 SQL 设计 | 生态、迁移和诊断工具不如 SQLite 稳定 | 不作为 V1 默认 |

## 影响

- 领域层只接收持久化端口，不知道 SQLite、文件句柄或目录实际位置。
- 任务状态不能仅由 UI 内存推导；每个安全检查点必须可回放。
- 清理器必须先计算活动引用，不能按目录名或文件年龄盲删。

## 退出条件

若目标文件系统无法满足页级提交或 WAL 恢复证据，必须收窄支持范围并形成新的 ADR；不得退化为整批盲重跑或覆盖源文件。
