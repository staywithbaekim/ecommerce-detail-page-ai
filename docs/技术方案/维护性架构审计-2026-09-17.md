## 结论

项目已经有清晰的基础架构，不需要推倒重写。当前维护成本上升的主要原因是功能连续加入后，应用编排和 WPF 页面没有同步拆分，导致多个稳定职责集中在少数热点文件中。适合采用“保留契约、逐步抽取、最后删除兼容路径”的重构方式。

本审计只记录结构事实和重构边界，不改变产品行为、数据格式、AI 提示词、RenderPlan 或 Photoshop 执行协议。

## 已存在的架构基础

- 工程已经划分为 `Domain`、`Application`、`Contracts`、`Infrastructure` 和 `Presentation`，并有架构测试约束依赖方向。
- `Domain` 不依赖 WPF、SQLite、HTTP、Photoshop 或供应商 SDK；`Application` 通过端口调用外部能力；`Infrastructure` 实现适配器。
- AI 结果、模板规则、尺码表和 Photoshop 执行之间已经有版本化合同。
- renderer-neutral `RenderPlan` 是稳定边界。AI、产品规则、批次状态和模板选择不应进入 UXP/Photoshop 适配器。
- 批次快照、SQLite checkpoint、manifest、资源 hash 和原子输出已经承担持久化与恢复边界。

这些边界应继续保留。重构的目标是让代码更符合现有边界，而不是重新设计产品架构。

## 主要结构问题

### 1. 主窗口 ViewModel 已成为应用容器

partial 只解决了文件长度，没有解决对象职责。主 ViewModel 仍同时持有模板、批次输入、AI、参考学习、结果、尺码表和凭据状态；构造函数还注入多个工作流和端口。新增功能如果继续放入这里，任何一个页面的修改都可能影响导航、命令可用性和全局通知。

### 2. 主 XAML 同时承载多个页面和弹层

页面通过大量 `Visibility` 绑定互斥显示。这样可以快速形成纵向链路，但控件树、绑定命名和窗口事件会持续累积，页面级回归也很难判断是局部问题还是主窗口状态问题。

### 3. AI 工作流同时承担编排和投影

`AiBatchAnalysisWorkflow` 既暴露用户命令，又负责上下文加载、恢复、调度启动、结果读取、状态转换、尺码表准备和 RenderPlan 准备。它是当前最容易继续膨胀的 Application 热点。`AiAnalysisScheduler` 的调度职责相对独立，但两者的生命周期和恢复入口需要更明确。

### 4. 新旧交互路径暂时并存

无限画布、旧人工校准、参考学习审核和普通模板编辑共享部分状态与事件。兼容路径在功能尚未完全验收前不能直接删除，但必须有明确的退出条件；否则每次修复都会继续增加条件分支。

### 5. 规模增长目前缺少“先抽取、后删除”的节奏

当前实现更常见的方式是增加可选参数、字段和状态分支。这在验收阶段可以降低回归风险，但如果没有后续删除阶段，代码量只会单向增加。重构后允许短期代码量上升，但每个阶段都要标出最终会删除的旧入口。

## 推荐的分阶段重构

### 阶段 0：冻结行为基线

- 保留当前 `RenderPlan`、SQLite migration、manifest、AI result 和 UXP/bridge 合同。
- 为每个页面记录入口、状态、命令、持久化事实和现有测试，不在此阶段改变业务规则。
- 在架构测试中增加“页面层不能直接读数据库/调用供应商”的约束，并记录主 ViewModel/工作流依赖数量作为趋势指标。

### 阶段 1：先拆 Application 热点

从 `AiBatchAnalysisWorkflow` 抽出四类职责明确的服务：

1. `AiBatchCommandService`：启动、暂停、恢复、取消、锁定和尺码图选择。
2. `AiBatchProjectionService`：从持久化结果构建页面投影和用户状态文案。
3. `AiAnalysisRecoveryService`：恢复 scheduler、checkpoint、manifest 和未知状态。
4. `AiRenderPreparationService`：校验确认结果、准备尺码资源并调用 `IAiRenderPlanFactory`。

原工作流先保留为兼容门面，内部委托这些服务；测试通过后再删除重复的私有实现。`AiAnalysisScheduler` 不和投影服务合并。

### 阶段 2：把主 ViewModel 降为 Shell

保留主窗口只负责导航、生命周期和页面切换；按页面形成独立的 screen ViewModel：

- `WorkbenchViewModel`
- `BatchInputViewModel`
- `AiAnalysisViewModel`
- `ReferenceLearningViewModel`
- `ResultsViewModel`
- `TemplateWorkspaceViewModel`
- `SizeTableEditorViewModel`
- `SettingsViewModel`

旧绑定可以通过短期代理属性兼容，代理被页面迁移后必须删除。页面 ViewModel 不得互相直接修改内部字段，只通过公开命令或页面状态接口通信。

### 阶段 3：拆分 WPF 页面

将主 XAML 按页面拆成 `UserControl`/`DataTemplate`，主窗口只保留导航壳、全局通知和生命周期级弹层。优先顺序是 AI 分析、模板工作区、批次输入、结果页，最后处理设置和低风险弹层。拖放、画布平移和缩放等 WPF 事件先保留在各自页面的 code-behind 或行为适配器，不把事件处理搬回业务层。

### 阶段 4：删除兼容路径

只有在对应验收证据已完成、重启和旧数据迁移已验证后，才删除旧人工校准入口、重复状态字段和旧绑定代理。删除必须单独成提交，便于回滚和审查；不得在抽取服务的同一提交中顺便改变产品行为。

### 阶段 5：收敛 Infrastructure 热点

最后再处理 SQLite partial、供应商适配器和文件副本代码。优先按端口/聚合边界拆分，保持 migration、checkpoint 和资源原子性不变。Infrastructure 重构不能反向把数据库类型泄漏到 Application 或 Presentation。

## 重构约束和完成标准

- 每一阶段开始前先有可运行基线；结束后至少运行受影响项目测试、架构测试和 `git diff --check`。
- 不以“总行数立刻减少”为单阶段目标。抽取阶段可能暂时增加门面和 DTO；删除兼容路径后才要求热点文件明显收缩。
- 新功能不得继续增加 `MainWindowViewModel` 的业务字段、`MainWindow.xaml` 的跨页面状态或 `AiBatchAnalysisWorkflow` 的新职责。
- 主窗口只依赖页面协调接口；页面只依赖 Application port 和只读投影；Application 不引用 WPF、SQLite 或供应商 DTO。
- 不修改 `RenderPlan` schema、AI 结果 schema、SQLite 历史 migration 或 Photoshop/UXP bridge 协议来换取更简单的重构。
- 任一阶段如果需要修改产品规则、提示词、数据迁移或输出语义，应另建任务和 ADR，不能混在维护性重构中。

## 暂不做的事情

- 不进行一次性“大爆炸”重写。
- 不为了减少行数删除仍承担验收和恢复职责的安全检查。
- 不在没有真实验收证据前移除旧入口或兼容读取。
- 不把 AI 颜色版本规划、模板学习或尺码表规则移入 UI 层。
