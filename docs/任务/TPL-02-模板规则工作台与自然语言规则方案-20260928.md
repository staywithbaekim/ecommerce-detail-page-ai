### 2.1 尺寸与响应式默认值

2026-10-01 覆盖旧总栏布局：保留预览优先、局部栏紧凑、输入悬浮与长页适宽滚动。A3 局部栏和卡片尺寸仅作历史参考，不能挤压真实内容；原 320px 总栏取消。下列尺寸为表现层建议，不是规则/数据库合同；[A 原型说明](../设计/TPL-02-A原型说明-20260928.md) 的旧总栏演示不再是当前验收依据。

- 卡片尺寸按实际客户区、DPI、长页和规则可读性确定，不把初稿宽高硬编码成产品约束。
- 预览优先占用卡片可用空间，局部规则栏紧凑但文字可读；保持原比例，不固定成窄条，不裁切模板。
- 不保留右侧总规则列，也不以默认折叠旧栏代替删除。
- 卡片间隔初始 12～16 DIP；尺寸统一在表现层资源定义。
- 按扣除主导航和边距后的实际可用宽度计算列数，不按屏幕物理宽度直接承诺列数。
- 宽窗口能放 3 列则放 3 列，放不下则 2 列；窄窗 1 列。不为凑列数缩小到看不清预览和规则。
- 用户已允许先由实现者定尺寸；以后调整样式/断点即可，不牵涉规则和数据库。

1920 屏幕在 125%/150% DPI 或有侧导航时未必能放 3 列。原型必须检查实际客户区，不能再次用示意图误导成“一个模块只能一行”。

### 2.2 PSD 卡片与局部侧栏

- 左上角圆圈编号（①②③），文件名和移除入口；不突出显示机器 ID。
- 不强制展示“单框/双框/三框/四框”标签，不要求填写“页面用途”。
- 有多少个有效可替换目标，就有相应规则行；固定背景、Logo、装饰和未经证实的智能对象不自动加入。
- 预览必须是完整 PSD 文档/合成预览，框线依据已验证替换目标的原坐标叠加，不按规则数量把页面重新分成二/四宫格。原型坐标示例必须明确标注，不冒充解析结果。
- 点击 PSD 预览中的框：定位本卡片侧栏对应行，滚动到位并高亮；点击规则行反向高亮框。
- 缩略图太小难以点中时可临时放大预览，仍保持模板上下文，不跳去另一套编辑流程。
- 局部侧栏独立滚动；到达顶部/底部时允许外层继续滚动，避免滚轮被困住。
- 框重叠时提供可替换目标列表辅助选中，不靠用户准确点中几像素边框。
- 新增规则只能绑定 PSD 中已有且受支持的目标；不意味着新建 PSD 图层。删除规则表示停止替换/保留模板内容，不删除源图层；若影响其他关系，立即产生可定位诊断。

局部侧栏只保留两类内容：

1. 本页用途：用简短人话说明这张模板什么时候用、用几次。同一 PSD 有多个分支/配方时在用途文字中写明，不能压成唯一旧 GenerationMode。
2. 逐框选图规则：框1、框2、框3……各自一条可直接编辑的选图短句。有有效框即出现编辑行，学习结果自动填入，未知有清楚空态；已确认绑定不重复登记。

不加入“调整目标框”“识别依据”“选图依据”“选中框更多细节”或常驻诊断区。底层结构校准与证据仍保留，不转成侧栏必填项；确有缺失或歧义，只在对应规则旁显示简短状态，不另扩一套面板。

框与规则采用同一选中状态，反馈要求如下：

- 未选中的有效框保留轻量框线和编号。某条规则获得编辑焦点时，只有对应 PSD 框使用清晰强调色边框、轻透明底和同号标签；该规则行同步强调，原选中框恢复普通样式。
- 输入过程中保持对应框高亮，不按每个字闪烁、不反复滚动或缩放。用户输入的是规则，反馈不是实时替换源 PSD，也不逐字触发 AI 或渲染。
- 长 PSD 中目标框不在可见区域时，仅在选择切换时把它滚入预览视口；已可见则不移动。键盘焦点和光标仍留在规则输入框，中文 IME 不被打断。
- 点 PSD 框内部即可选中，不要求点细边线；本卡片侧栏滚到对应规则并高亮，用户可直接编辑。不跳旧编辑器、不展开详情，也不改变其他 PSD 的编辑状态。
- 鼠标悬停可有轻量预提示，但不改变正式选择、不触发滚动；编号与边框同时表达关联，不只依赖颜色。

#### 2.2.1 长 PSD 的已确认行为

- 默认适宽，不为整张塞进卡片而缩成细条，也不让卡片无限增长；原文档在有限预览视口内纵向滚动。
- 视口暂时只展示一段不等于裁剪源内容。保留真实宽高比、原 PSD 自带留白及固定内容；去掉的是 UI 额外边距，不是修改 PSD。
- 点击规则/@框引用时同步定位到文档对应区域；点击框线反向滚动并高亮本卡片规则。
- 提供适宽/整页和临时放大；整页模式为用户主动缩览，不作为长页默认可编辑视图。
- 预览与规则栏独立滚动；到顶部/底部时允许继续滚动外层。末尾内容必须能滚到悬浮输入框上方。

### 2.3 统一导入与增删

用户只看到一个“导入模板组”入口，不先弹菜单让其选“文件/文件夹”。

- 工作台和输入框均接受一个 PSD、多个 PSD、整个文件夹的拖放。
- 点击入口进入统一导入界面，可加入文件和文件夹，不暴露两条业务流程。
- 实施时核对原生选择器能力；如果不能在同一个系统选择器混选文件/目录，不伪称支持。用同一导入容器接受路径与拖放作为补足，不强推用户两选一菜单。
- 文件夹默认只读取直接包含的 PSD，避免悄悄合并多个模板组；发现子目录时在同一导入区域提示可包含子目录，并显示待导入清单。
- 同 hash 可以复用资源，但“资源去重”不等于悄悄合并用户有意创建的页面身份。
- 普通重复拖入可提示已存在；同 PSD 多次输出通过规则实例化，不要求重复导入文件。
- 文件不可读或结构不支持时只隔离该项，保留其余成功项，给出原因和重试入口。
- 删除 PSD 只移除当前草稿页面；显示受影响的引用，并支持撤销。不删除电脑原始文件和历史版本资源。

### 2.4 @ 引用

- 输入 @ 弹出编号、名称和缩略图候选；选中后成为绑定稳定 ID 的引用标签。
- 支持 @1、@2、@1 的框1，以及多模板引用；内部保存 PageId/FrameId，不靠字符串相似匹配或当前数组下标。
- 编号与输出顺序分离：删除 ② 后不把 ③改成②；新导入使用未用编号。重新排序不换引用目标。
- 模板包导入生成新内部身份时，同步重映射所有引用；编号保留或显式映射。
- 被删除对象的旧引用显示失效，不自动改指其他模板。
- “上面/下面/左边/右边”只有目标唯一可辨时解析；不明确时只追问相关指向。

### 2.5 自然语言与手工编辑共存

- 底部统一输入框为主交流入口；局部规则直接手工修改，总览节点可定位对应条件/模板/框原位修改。
- 输入框以大圆角/阴影浮在工作区底部，内容延伸到后方，不设置占用固定高度的底部分区；只在滚动内容末尾提供必要可达余量。输入多行或引用标签增加高度时同步调整余量。
- 不再额外增加另一份独立的“全局提示词”作为第二真相来源。
- 手工修改立即更新草稿及派生摘要；发送新消息只修改明确涉及的范围，不把以前所有规则重置。
- 新 AI 响应显示简短“已更新 @2 的框1、@3 的使用条件”，可撤销本轮修改；不弹逐框确认。
- 同一字段有明确新指令时按新指令修改；不同来源/范围发生真实矛盾时指出矛盾，不用暗藏的优先级替用户做业务决定。
- 无 API 或请求失败时仍可人工建立合法规则并保存草稿，不把所有编辑按钮锁死。
- 普通 PSD 结构扫描是本地处理；AI 语义读取按现有上传授权与计费边界执行，不因导入就悄悄发请求。
- 输入框移除常驻“取消”按钮，保留发送及必要处理状态；不删除内部取消、安全退出或导入弹窗取消。撤销修改不作为第二个常驻输入按钮。
- 接回既有参考学习和本款素材分析；文本规则解释不能凭空识别没看过的 PSD。展示短句与内部颜色/资源约束分开，不能把未解析的“指定颜色”当最终选图依据，不为每个框无理由新增付费调用。

### 2.6 默认采用与最后一次确认

- 结构有效、规则可解析的结果默认采用，用户无需逐框/逐页勾选。
- “默认采用”是交互策略，不等于已完成图层验证、凭空生成缺失规则或允许直接渲染。
- 草稿可自动保存；即使有问题也允许保存草稿，不能让用户白做。
- “查看总规则”进入工作区内的关系总览：小组大括号 → 使用条件 → 模板与次数 → 每框选图，详见 §2.7。不再是窄文字弹窗或另一套编辑器。
- 总览节点可定位回卡片；只有“返回修改”和“确认并保存模板组”两个主要动作，不要求再点所有节点。
- 确认针对当前 DraftVersion 和 RuleDigest；确认期间有新修改，必须刷新总览，不能提交用户没看过的版本。
- 未解决结构错误/规则矛盾/失效引用阻止“发布可用模板”，但不阻止“保存草稿”。
- 仅靠低置信分数不强制逐框确认；实质歧义才要求补充信息。

### 2.7 最终规则关系图

- 首要目标是让用户看懂 agent 对要求的理解，且复述与真正执行使用同一份规则，不是为了画导图强迫用户套固定模式。
- 常规“各模板用一遍”应直接表现为各模板一次及其逐框选图；“同模板用多次”表现为重复对象/次数和每次差异；“不同情况选不同模板”表现为条件分支；组合、顺序及这些规则的混用也按真实意图表达。具体款事实尚未导入时显示可计算的规则，不编造实际次数或选图结果。
- 简单规则用简洁结构，复杂规则才展开分组和条件，不能把所有任务都塞进单/双/三/四色示例。歧义只针对不明确的那一点提问；当前不支持的要求明确说明，不能先肯定复述再静默换一种执行。
- 类似思维导图，用大括号或等效分组连线把同一使用逻辑的模板归组并写明名称；它表达规则，不是“导入→分析→生成”的线性流程。
- 能看清使用条件、选择哪张模板、重复次数、输出顺序、每框选图和同色关系；明确区分互斥选择与组合生成。分为一个小组不等于全部都生成。
- 单/双/三/四模板只是小组示例，不是固定四种模式，框数不等于颜色数，同一 PSD 可出现在多个配方上下文。
- 示例：若规则约定按待展示颜色数选择，则 1 色→单色模板、2 色→双色模板、3 色→三色模板、4 色→四色模板；5 色未定义时提示覆盖缺口，不能擅自选 4 色。示例不冒充用户实际 PSD 解析结果。
- 模板节点可展开全部框规则；有目标款时才展示真实颜色/命中素材，建模时不虚构资产或产出数量。点击节点定位原卡片/原框，修改同步；支持展开/收起，不要求用户自己拖线编程。
- 图、小组和条件均派生自同一结构化规则；先表达既有 branch/recipe 关系，不另建分组数据库、独立规则文本或平行执行协议。最终按当前版本确认整个模板组一次。

## 3. 建模与生产两个阶段，门禁不要混淆

### 3.1 建立可复用模板

    新建/编辑草稿
    → 导入模板并本地读取结构/预览
    → 可选导入参考素材、AI学习规则，或直接自然语言/手工填写
    → 局部侧栏与规则关系总览同步
    → 结构与规则校验
    → 总览一次确认
    → 提交模板修订

可以没有代表素材先建规则。源照片不是模板保存的强制前置；没有本款尺码图也不应阻止模板保存，因为真实款式数据还没导入。

尺码 PSD 复用解析、学习与校准，能确认的目标区域、布局和样式自动采用；仅结构确有歧义时在当前卡片提示修正，不增加正常流程配置页。模板旧数值不能当成目标款尺码数据。

### 3.2 日常正式生产

    选择已保存模板组
    → 导入目标款商品素材、选择输出位置
    → 批次冻结模板版本
    → AI分析目标款，推荐主色并允许更改
    → 系统确定颜色归属及同款尺码来源（仅歧义/缺失原位提示）
    → 根据结构化规则展开输出页实例
    → 为每个实例的每个框匹配图并校验
    → 预检
    → 确定性 RenderPlan
    → Photoshop/UXP 执行、提交输出、结果展示与恢复

- 不要求每款/每框再走模板建模确认。
- 普通照片和尺码来源共用本款文件夹/素材列表，复用识别与唯一可靠来源自动选择；不强制独立尺码目录或第二次导入，内部来源校验仍保留。
- 参考素材不得混进目标款选图，预览图不得成为正式高清源图。
- 某副色缺反面时只隔离受影响输出实例；不能借另一个副色反面补齐。
- 尺码数据缺失、多候选冲突或识别不可靠在生产阶段提示；不猜尺码值、不回填其他款数据。
- 延续现有动态尺码确定性排版与目标区域逻辑，不承诺所有模板都逐文字层替换；客户看到的结果是按本款尺码图换数据、沿用模板样式。
- 默认沿用尺码页每款一次；如用户明确表达其他生成条件，走同一规则校验而不是隐藏改写。

## 4. 必须独立验证的需求样例

**以下是不同场景，不要把它们机械拼在同一个示例里。图片框数量不等于可容纳颜色数量。**

### R1：模板内不同颜色

输入：“@1 左框主色正面，右框副色正面。”

至少表达两个颜色角色，不能把整个 PSD 锁成一个 VariantId。若存在多个副色而用户尚未指定右框选哪个或是否轮换，结合已给的模板组规则解析；仍不唯一时只追问这个缺口，不私自永远取第一个副色。

### R2：仅有单颜色展示与双颜色展示两个 PSD

前提：@1 放一个颜色的正面，@2 两个框分别放两个颜色的正面。

用户规则：“奇数先用 @1 放主色，剩下两两用 @2；偶数全用 @2，主色排第一个。”

| 颜色数 | 预期输出组合 |
| --- | --- |
| 1 | @1 × 1 |
| 2 | @2 × 1 |
| 3 | @1 × 1 + @2 × 1 |
| 4 | @2 × 2 |
| 5 | @1 × 1 + @2 × 2 |
| 6 | @2 × 3 |

主色第一，副色没有业务排名；执行使用冻结的稳定顺序，重启不能重新随机配对。默认保证已识别颜色按该规则覆盖且不重复、不丢失。颜色数量为 0 或分组不确定时不编造分组。

### R3：按颜色数选 @1/@2/@3/@4

用户可以说：“一个色用 @1，两个色用 @2，三个色用 @3，四个色用 @4。”

这些 PSD 的框如何选图仍按各自规则，不强制界面选择“单/双/三/四模式”。五色以上没有定义时，提示需要补充规则，不擅自套用 R2。可以用自然语言追加具体配方或可组合的通用规则。

### R4：每个副色一张同色正反面页

输入：“@5 每个副色生成一次，上面该副色正面，下面同一个副色反面。”

- 两个框共享一个颜色槽位，且只遍历副色。
- 5 个颜色＝1 主色＋4 副色时，@5 生成 4 次，不是 2 次。
- 6 个颜色时生成 5 次；只有主色时生成 0 次。
- 每个实例内两个框引用相同 VariantId，但不同视角资产。

早前讨论中把“@2 每个副色一次”和“五色 @2 两次”混在同一个例子是不成立的：在 R4 中四个副色需要四次；在 R2 中一次容纳两个副色才是两次。**不要把这段历史示例写成实现规则。** 系统必须识别此类覆盖与次数冲突。

### R5：尺码页

输入：“@6 根据本款尺码图换尺码数据。”

延续现有尺码识别、来源选择、结构化数据和确定性排版。没有目标款素材仍可保存模板；正式出图时验证尺码来源。保持其他非目标图层，不猜数值。

## 5. 长期架构：重构工作台与补齐规则层，不推倒重写

### 5.1 分层和唯一职责

    WPF 组件/页面 ViewModel
      → 模板工作区应用用例（导入、草稿、补丁、验证、提交）
        → 领域规则与确定性编排器
        → AI解释端口（Infrastructure 实现）
        → 现有模板持久化端口/SQLite 实现
      → 生产匹配及输出实例编排
        → 既有 RenderPlan 构建/验证
          → 既有 Photoshop/UXP 适配器

- UI 不写 SQL、不硬编码选主副色、不直接调用模型或 Photoshop。
- Application 定义用例/端口，Domain 定义有效规则与不变量，Infrastructure 负责 HTTP/SQLite/文件。
- 复用既有服务和 writer；不要为了名字好看新建第二套任务调度器、仓储框架、数据总线或规则引擎平台。
- 新类名在 B 阶段核对后落地，本文建议名不是要求先生成大量空类。

### 5.2 一份业务规则，多种展示

- 保留 TemplateGroup / TemplateRevision / TemplatePage / FrameBinding。
- 既有 FrameBinding 继续拥有图层结构、布局与框选图要求；补充类型化颜色约束时也必须明确其唯一归属。
- 新 TemplateRuleSet 主要拥有跨模板编排：条件、循环范围、配方、输出顺序和框之间的颜色绑定关系，引用 PageId/FrameId，不复制 PSD 内容。
- 客户原话、AI 来源记录是审计输入；不是另一份可以绕过校验执行的规则。
- 卡片侧栏、分组关系总览和编排器读取同一聚合，不另存可独立编辑的总规则；取消右总栏不改变规则所有权。
- 摘要文本/流程图是派生视图，不作为执行输入；可缓存但必须按规则版本失效。
- 如仍需给现有 AI 选图接口提供描述文字，应由权威结构化规则生成并带版本，不让旧自由文本与新字段各自独立变化。

### 5.3 规则表达能力及边界

V1 采用有边界的类型化表达：

- 条件：颜色数量比较/范围，以及明确支持的素材存在条件。
- 范围：主色、全部颜色、仅副色、当前迭代颜色、配方分配到的颜色槽位。
- 执行：每款一次、按颜色遍历、明确组合/次数。
- 框要求：正面/反面/局部等自然语言图像语义 + 类型化颜色/同组约束。
- 关系：同色、不同色、覆盖不重复、主色优先、输出顺序。
- 尺码：复用既有独立数据通路。

每个颜色槽位可绑定多个框，例如正反面两个框共享一个槽位；另一 PSD 两个正面框可各绑一个槽位。这是系统内部模型，不要求客户选择“模式”。

不支持任意脚本、SQL、无限循环或 AI 动态代码。不能支持的需求直接说明，保留原话供后续扩展；不静默忽略。未来新增规则类型通过显式 schema 版本/迁移，不许把未知规则当普通备注继续出图。

### 5.4 自然语言采用补丁，而不是每次重建整组

建议应用用例（命名可随既有约定调整）：

- InterpretRules：输入用户文本、必要上下文、稳定引用表和草稿版本，返回类型化操作/诊断。
- ApplyRulePatch：携带 CommandId、ExpectedDraftVersion；校验后原子应用、更新版本，支持撤销。
- ValidateRuleSet：纯规则/结构校验，不依赖 Photoshop。
- BuildRuleOverview：从同一份有效草稿生成流程图数据。
- CommitTemplateDraft：复用既有提交链路，冻结当前规则与摘要。

AI 返回目标必须属于本次允许的页面/框集合；字段、类型、数量和引用严格校验。禁止 AI 扩大修改范围、生成未知 ID 或直接改数据库。

### 5.5 AI 调用、编辑并发和费用

- 复用当前供应商适配、凭据、上传授权、请求日志、费用/usage 和未知结果规则，不新建绕过这些的 HTTP 入口。
- 规则理解是独立任务合同，不复用旧响应 schema 冒充支持新能力；模型/提示词/上下文/schema/草稿摘要纳入请求与缓存身份。
- 文本规则解析优先只发必要文本/结构元数据。确需视觉学习时沿用受控分析副本，不上传完整 PSD、绝对路径、密钥或全部历史聊天。
- 发送期间用户改了规则、删了页：旧响应不能覆盖新草稿。使用 ExpectedDraftVersion/CAS，显式重算或安全重新验证。
- 重复点击按 CommandId 幂等；解析失败不抹掉旧规则；撤销按操作而不是按整组重置。
- 超时、取消、限流显示可理解状态；AiResultUnknown 不自动重发，不把付费请求当免费重试。
- 不靠无限加长聊天上下文记住规则。当前结构化草稿为主要上下文，历史记录只作有限来源追溯。

### 5.6 API 能力分工与服务商可替换（2026-10-01 用户明确方向；待代码改造）

目标是应用级垂类 agent，而非自建基础模型、视觉识别平台或模型服务。是否采用 API 取决于任务准确性、延迟、成本和证据；不因“本地实现”而优先堆图像启发式，也不因“agent”而把确定性文件操作交给模型随意决定。本节明确实施要求，不表示 GPT 或任意供应商已经接通。

| 能力 | 模型/API 负责的部分 | 应用必须保留的部分 |
| --- | --- | --- |
| 自然语言规则 | 理解意图、解析上下文、提出规则修改及必要澄清 | 操作范围/稳定引用、合同与业务校验、版本/CAS、实际差异和总览派生 |
| 模板参考学习 | 基于必要图像与框上下文理解未来选图语义，辅助判断商品内容 | PSD 结构/图层/蒙版/坐标读取、文件归属和受支持绑定，不把每个智能对象当目标 |
| 目标素材与选图 | 联合理解同款照片的颜色、真人/假模、正背、姿态、部位，给候选与主体证据 | 目标款/颜色/实例范围、人工锁、资源 hash、原图选择、确定性 placement；不跨款补图 |
| 尺码理解 | 从受控分析副本提取可见文字与表格结构，识别来源歧义 | 逐格来源、冲突/缺失校验、结构化数据版本和确定性排版；不猜值、不生成虚假尺码 |
| 结果辅助质检 | 适用时识别疑似错图、异常裁切等语义问题，提供复核线索 | 尺寸/文件/hash/实例归属检查、真实输出证据及用户视觉确认；模型不能自行宣布验收通过 |

复用现有 IAiServicePort 及版本化任务/结果合同。业务只表达“规则解释、参考学习、目标分析、尺码提取”等任务，不引用供应商 DTO、端点或 SDK。供应商 adapter 负责请求格式、视觉输入、结构化输出、用量/错误/未知结果映射；不要在 UI、模板规则或执行编排中散布供应商判断，也不并行新建第二套 AI 请求/预算系统。

当前差距已核对：DesktopServices 直接注册 VolcArkAiAdapter；VolcArkAiOptions 校验固定模型；ReferenceLearningAiService.ModelConfigVersion 固定豆包，模板规则协议沿用该值；ADR-015/019 的现行配置和上传说明均以方舟为生产基线。因此“有中立接口”不等于已经可安全切 GPT，不能只改 URL 或放开固定模型校验就宣称完成。

改造约束：

1. 已实现并通过合同/真实样本验证的供应商，运营切换只需选择受控 provider/model 配置及对应凭据；新供应商首次接入仍需要 adapter 和测试，但不重写模板、批次、选图业务或 Photoshop 链路。未知端点和未验证能力不能冒充兼容。用户只要求可替换架构，不据此增加一整套复杂高级设置 UI。
2. 能力与版本显式识别：文本/视觉、图像数量/尺寸、结构化输出、上下文/时限等必须满足当前任务。能力缺失在请求前可行动拒绝；不能把 SDK 名称相似当作支持，也不因换供应商放宽产品安全边界。
3. provider/model/config、提示词、结果 schema、任务种类及输入/规则摘要参与请求和缓存身份；历史方舟记录按既有版本解释，不静默改写其含义。请求开始时绑定配置，待处理/Unknown 恢复不能因全局配置切换而换商重发。
4. 凭据按供应商隔离，使用现有安全存储；上传说明和准入绑定实际目的地/用途。用户允许必要付费 AI，不等于可以把方舟专属授权直接当作任意新目的地的上传授权；同一已明确范围不重复询问。
5. 用量与费用保留供应商、模型和币种/定价配置依据，继续经过原请求账本、预算、取消、限流、硬截止及 Unknown 门。未决请求不自动切另一个模型重做；禁止由自动 fallback 造成重复付费或无法对账。
6. 规则学习可复用；同款素材优先联合分析后供多个框复用，缓存按真实身份命中；只补必要信息，不无理由每框单独付费调用。人工输入和框高亮仍是本地即时反馈，不逐字触发 API。
7. 不新增通用多 agent 平台、自动模型竞价/路由、账号支付或自建云网关；首要目标是单一当前配置、可替换 adapter 和一致任务结果。质量/速度不能靠架构声明保证，换模型必须通过同一组真实任务样例。

实现验收须覆盖正式 DI 到统一端口、至少两种适配实现的对应任务合同（不能靠两个不同名字的同一 mock 充数）、配置/缓存/凭据隔离、能力不足拒绝、切换后旧任务恢复不串商，以及已确认 UI/规则行为不变。离线 adapter 合同验证与真实 provider 样本证据分别记录；没有真实请求证据就不宣称该供应商已验收。当前仅完成代码核对和此方向落盘，未修改生产代码或启用新服务商。

## 6. 持久化、查询、更新和兼容

### 6.1 建议最小持久化方案

实施前对照现有 schema 决定精确表结构，不预先创建三张用途重叠的大 JSON 表。

| 数据 | 权威位置/建议 |
| --- | --- |
| 模板组、修订、页面、资源、框结构 | 复用既有表与资源存储 |
| 跨模板规则 | 每修订一份带 SchemaVersion 的规则集；包含可校验摘要 |
| 编号映射 | 与草稿/修订关联的稳定 alias 映射；若需查询用关系字段 |
| 框级选图规则 | 延续 FrameBinding 所有权，新增类型化字段须与描述保持单一写入口 |
| 草稿编辑 | Version + CommandId；同一 writer 事务原子保存 |
| 解析来源/撤销信息 | 优先扩展既有请求/事件存储，必要时新增最小附属记录 |
| 总览、诊断 | 默认按版本计算；若保留历史证据，应明确不可作为第二份规则来源 |

规则集可用严格版本化 JSON 保存复杂条件树；经常按页面/框查影响的引用建立受约束的关系索引/投影，并与规则集同事务更新。不可使用随意键值 EAV 或 UI 直接解析 JSON 查询业务。

只建立真实读写路径需要的主键/唯一键/索引，如 revision_id、目标引用、CommandId、草稿版本；不要给所有字段盲目加索引。必须支持“删除模板前查所有受影响规则”“按修订读取完整规则”“恢复精确版本”。

### 6.2 事务和来源

- 规则补丁、框更新、alias 更新、草稿版本推进同一事务，失败不出现半新半旧。
- 修订提交复用既有不可变修订和当前指针原子切换。
- RuleDigest 覆盖所有影响输出的规则、图层绑定和顺序；不包含卡片尺寸、滚动位置、UI 高亮或机器绝对路径。
- 数据日志要有保留范围、脱敏与清理规则，不能无限存全量模型响应/图片 base64/聊天内容。
- UI 布局是偏好，不进入业务规则，也不因调卡片宽度使全部模板重新提交。

### 6.3 历史快照与模板包

- 已提交修订不可原地修改；旧批次读取原快照，不追随当前模板组指针。
- 新 schema 使用追加迁移，不改旧迁移编号、checksum 或历史 journal 字节。
- 在隔离数据库副本测试升级/中断/恢复；本方案阶段不迁移正式库。
- 旧数据的 CanvasX/CanvasY、Notes、VariantCapacity、GenerationMode 暂留读取兼容，不急删列。
- 旧模板通过显式适配进入旧语义；不能无证据把旧备注解析为新规则。
- 新模板包需包含有效新规则并重映射稳定引用；不能放在旧包 notes 字段里偷偷传递。
- 旧版本不支持新规则时应明确拒绝，不静默丢规则、降级生成。
- 批次、manifest、审计快照为恢复需要的不可变副本，不属于应删除的冗余；但要通过 digest/版本保证一致。

## 7. 编排与 RenderPlan：重复模板不等于重复投同一页

### 7.1 新增业务编排结果，保留执行合同

规则编排器根据冻结规则与目标款事实，生成明确的“输出页实例”列表：

- PageInstanceId（建议概念名）、来源 PageId、规则分支/配方项；
- 该实例的颜色槽位 → VariantId 分配；
- 每个框 → 对应图像要求和最终 AssetId；
- 输出顺序、可生成/阻断原因；
- 规则/输入事实版本与摘要。

同一个 PSD 使用三次必须产生三个不同逻辑实例，不得以 PageId 唯一键覆盖结果。输出文件名、页面计数、预览导航、journal、checkpoint、恢复、公开发布都必须核对实例身份。

### 7.2 不把业务循环下沉到 UXP

优先由 Application 展开多个独立 RenderPlan，保持 render-plan/v1 的“执行一个明确计划”语义。**不要随意往 RenderPlan 加 repeat_count 或用户自然语言让插件解释。**

先审计现有身份及快照合同能否表达组合实例；不能表达时先补兼容决策/ADR、Schema 与迁移，再接执行。绝不把多色拼版硬塞为单一 OutputVariantId，或用同一执行 ID 多次投递。

### 7.3 确定性与可解释性

同一冻结规则 + 同一商品事实 + 同一人工覆盖，应产生一致的实例顺序、颜色分组和内容摘要。计划身份按既有创建/幂等规范分配并持久化，恢复时复用已登记身份，不重新生成一组随机 ID。

“副色不分主次”表示客户没有排名要求，不意味着每次随机配对。所有实际颜色分配在预检和恢复中可追溯。

有规则冲突时总览显示冲突分支；有商品缺图时显示受影响的实际输出实例，不静默少生成几页而仍标全部成功。可增加按 1～6 色的规则演算帮助检查，但该演算不是实际 AI 选图或 Photoshop 验收。
