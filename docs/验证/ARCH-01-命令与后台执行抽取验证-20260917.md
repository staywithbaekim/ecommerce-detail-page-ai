## 独立诊断与修复

触发条件是页面刷新先读取了旧调度快照，随后结果读取已经看到首层分析完成。用于展示的请求仍可能是初始化时的占位请求，其 ConsentId 为 consent-pending。原精细分析命令直接从该内存请求集合取父请求，子请求继承占位标识；下一次刷新取得真实父请求后，现有父子引用检查会拒绝两者不一致，形成“主体分析结果不可用”。

集成测试通过 `DelayedSchedulingReads` 仅滞后工作流的调度快照读取，真实 scheduler、SQLite 与结果文件链继续正常完成。用户命令前恢复最新调度读取，以固定“结果已完成、内存请求仍旧”的前置状态；没有增加等待时限或关掉一致性检查。

- 修复前两场景：正常 1 通过、受控滞后 1 失败。失败明确为父请求正式 ConsentId 与子请求 consent-pending 不同。
- 修复：三处选图/尺码来源/精细分析命令调用异步父请求读取，直接从本批次持久化 HistoricalRequests 取实际首层请求；无历史记录时保留原内存回退。命令使用本次读取的局部结果，不依赖另一刷新恰好更新共享字典。
- 保留原父子引用检查、授权检查、人工锁定规则和未知结果不重发。没有改请求/schema、fingerprint、scheduler 或持久化实现。
- 修复后、抽取前工作流/RenderPlan 集成组 34/34；抽取后同组再跑 34/34；最终完整 Infrastructure 包含该两场景，301 通过/5 跳过。

修复工作流由 675 行变为 688 行（+13）。已将修复后内容另存为抽取对照基线，避免把行为修复混写为纯迁移。此前失败记录继续保留；本次关闭具体的占位父请求不一致路径，不宣称所有并发风险均已排除。

## 抽取与所有权

| 组件 | 职责与所有权 |
| --- | --- |
| AiBatchAnalysisWorkflow | 保留公开构造函数/接口、批次加载和缓存、投影与渲染准备组合、全局取消与释放顺序 |
| AiBatchCommandService | 每批次命令、请求/终态错误集合、Started 状态，拥有 scheduler、恢复服务和后台执行器，提供不可变事实快照 |
| AiBatchBackgroundRunner | 拥有 admission/consumer 任务、准入取消源、启动门和运行错误集合；借用 batch/template/scheduler 与应用关闭令牌 |
| AiAnalysisRecoveryService | 保持第三条的恢复锁、一次尝试及共享错误语义，借用同一 scheduler |

保持的执行顺序：

1. 门面在原上下文创建锁内加载批次/模板、创建 scheduler 与命令服务，登记缓存后刷新请求。
2. 开始/刷新/控制入口按原顺序恢复调度器与 checkpoint；人工选择、精细分析和渲染准备仍保留原有的恢复覆盖范围。
3. 开始在检查就绪/授权及请求刷新后启动后台工作，返回页面投影；不等待整批素材准备或 provider。
4. admission 仍只启动一次；consumer 在队列暂空时保持存活，暂停/离线/取消时保持原等待分支。并发上限、延迟、重试和异常映射均不变。
5. 关闭仍全局取消 → 所有批次停止 admission → 逐个任务最多等待 5 秒 → 统一释放 scheduler、恢复锁和取消源；未延长等待或修改超时后的既有释放行为。
6. 渲染准备仍先恢复/刷新，再读取投影，最后捕获请求数组传给原渲染服务。不宣称跨投影/数据库具有原子快照一致性。

命令体、后台循环和原私有可变 BatchContext 已从门面删除；没有保留平行 fallback 或把可变运行上下文作为新服务参数。命令服务不调用投影/RenderPlan 服务；后台执行器不持有命令服务、投影或渲染能力。公开门面仍有调用方，本轮保留。
