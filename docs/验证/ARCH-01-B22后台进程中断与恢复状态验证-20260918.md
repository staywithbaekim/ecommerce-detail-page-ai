# ARCH-01 B-22 后台进程中断与恢复状态验证（2026-09-18）

## 结论

真实进程中断验证发现并修正一处原有显示缺陷：请求到达 provider 边界后进程退出，重启会安全保留未决账本且不重发，但页面仍显示“分析中”。现在重启后显示“结果未知／需要恢复”，并继续阻止自动重发和生成。此项是独立于 B-21 兼容删除的恢复显示修复，对应 PRD 18、22.4 的恢复要求；不修改持久化状态、重试规则或外部合同。

## 中断证据

仓库外 `详情页/tmp/arch01-b22-interruption-20260918/probe` 使用当前源码的工作流、命令服务、后台执行器、生产 scheduler factory、WIC 分析副本、SQLite、checkpoint 和 manifest。输入由 Domain/Store API 建立最小单款单框夹具，素材是 B-20 已批准照片的额外副本。输入仓库直接使用 SQLite store，未验证正式扫描提交链；provider 替换为可控的等待边界，不读取凭据、不发网络请求，不生成产品图片或 PSD。

1. 新进程启动后台工作，在 provider 调用入口暂停。确认账本 `Analysing`、pending=1、预算请求计数=1、边界调用=1 后，写入证据并调用 `Environment.Exit(73)`，不执行服务 Dispose。`dotnet run` 外层报告非零退出，73 是探针明确请求的内部退出码。
2. 另一进程打开同一 SQLite/manifest，依次执行 Refresh、Resume、Start、Refresh。修复前四次均显示 `Analysing`；provider 再调用=0、预算仍为1、checkpoint=Committed、数据库完整。这证明不重发边界有效，但恢复展示未通过。
3. 修复后使用同一中断数据，两个独立新进程各执行相同步骤，四次均显示 `RecoveryRequired`，提示不会自动重发。两次 provider 调用均为0、HTTP为0；账本仍为 `Analysing`、pending=1、预算计数=1、checkpoint=Committed，源 hash 不变，无正式输出。

原始记录：`before-interrupt.json`、修复前 `recover-report.json`、修复后 `recheck-report.json` / `recheck2-report.json` 和 `boundary-calls.jsonl`。修复前源文件快照与独立差异为 `before/`、`review.diff`。对照 HEAD 的工作流，原有 `Uploading/Analysing → 分析中` 分支相同；修复前 scheduler 相对 HEAD 无改动，不能归因于本轮重构引入。

探针准备时修正了临时路径末尾分隔符和夹具 manifest 引用格式，错误夹具没有进入 provider。修正的是测试输入，不是放宽生产门禁；旧失败目录保留为诊断材料。最终中断数据来自新的独立数据库。

## 修复边界

- scheduler 恢复时把仍为 `Uploading/Analysing` 的请求 ID 记录为不可变的运行时事实；该集合每次恢复重新建立，不加入 SQLite、AI 结果或调度持久化 schema。
- 命令服务将该事实随不可变快照传给投影服务。投影仅对仍未决的这些请求采用既有未知结果展示，覆盖整款理解、主体几何补充和尺码提取；正常在途请求仍显示进度，后来得到已确认结果时以最新账本为准。
- 账本原值、pending、预算、checkpoint、租约、排队/重发和取消语义保持原样。已完成页面不会因另一请求的中断被全部改成错误；既有人工锁定投影仍保留。
- 没有新增 provider/API 请求或正式 Photoshop 行为，未修改源 PSD、原始照片及正式输出。本轮生产 C# 增加36行，当前178文件/51,318行；与 B-20 比净减967行，与初始48,870行比仍增加2,448行。Shell仍为560行。
