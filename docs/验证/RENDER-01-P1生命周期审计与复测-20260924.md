## 实际调用链

```text
RenderBatchCoordinator.RunAsync
  -> sessions.OpenAsync（每次批次运行一次，不是每页一次）
     -> CreateTaskOwner -> StartAsync -> listener/sessions/broker
  -> 已有执行恢复（Unknown 不重投）
  -> 每页 IsReadyAsync -> owner.GetStatusAsync
     -> 本地会话状态；不是再次握手或重启 listener
  -> SubmitAsync -> 准备受控副本 -> owner.SubmitPageAsync
  -> UXP tick -> claim/ACK -> 校验并领取资源 -> Photoshop 单页执行
     -> 输出上传/封存 -> page_completed
  -> ObserveAsync -> 独立输出验证 -> 原子提交 -> execution_completed
  -> UXP observeCommit -> 核对身份/序号/唯一完成事件 -> 清理 -> ready 心跳
  -> 桌面确认释放 -> 页终态；最后一页后 dispose owner/listener
```

必须区分以下等待：

| 位置 | 原行为与证据 | 决定 |
| --- | --- | --- |
| 冷启动/首次 ready | 批次创建一次 owner；首次认证要求至少三次心跳。P1 基线包含人工连接等待 272.533 秒 | 保留认证门；不把人工操作等待算成 Photoshop 开销，也不承诺它全部可优化 |
| Coordinator ready/观察循环 | 本地状态查询，未变化时 250 ms；不是每次重新解析 PSD | 本轮保持；新增可选查询计数/耗时埋点，测量后再决定 |
| UXP 工作循环 | `main.js` 用 5 秒 `setInterval` 驱动整个 tick，提交查询和下一页领取也被该周期限制 | 从心跳节奏中分离工作调度 |
| `output.wait_ready_ack` | P1 基线 7 次合计 20.3497648 秒；单次约 1.505–4.222 秒，平均约 2.907 秒 | 保留清理确认，缩短其生产者的固定查询等待 |
| 输出验证/提交 | P1 基线验证合计约 0.212 秒、提交约 0.605 秒，远小于上述等待 | 不删 hash、解码、尺寸、ICC、manifest/marker/checkpoint |

旧基线为 `tmp/r01-render-perf-20260924-p1-r1/render-performance.json`。其中 `output.wait_ready_ack` 是旧构建的真实记录；接续时源码中没有此字段，是原线程已做未验收删除造成的差异，不是埋点自动消失或已证明性能改善。

## 最小改动

1. `uxp-render-adapter/src/main.js`：配对后安排首次 tick；之后仅在前一次 tick 完成且会话健康时，使用 250 ms `setTimeout` 安排下一次。保留 `inFlight`/`busy`、单页串行、断线停止；不并行打开 Photoshop 文档，不自动重连/重放。
2. `work.js` 的普通心跳仍按 5 秒限流；执行安全边界的强制 pulse 保持。250 ms 是有界工作查询间隔，不是将心跳改成每秒四次。
3. `BridgeRenderBatchSession` 在提交**之前**取得心跳基线；`BridgeSessionOwner.WaitForReleaseAsync` 接受之后匹配的认证释放心跳。这样已经在 commit 返回前到达的合法 ACK 不会被错误要求“再等下一次心跳”。仍需 Connected、Ready、新心跳和匹配的完成事件序号；20 秒截止/取消/断线继续安全失败。
4. 可选 `RenderPerformance` 增加 `bridge.owner.start`、`bridge.owner.dispose`、`bridge.status`、`bridge.executions.list`。无诊断 ActivityListener 时不持久化诊断，不记录路径、图片或凭据；完整计数取自已完成 r2，不从中断批次补造。
