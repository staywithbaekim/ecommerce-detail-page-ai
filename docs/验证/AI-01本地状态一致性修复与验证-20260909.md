## 已确认的根因

- 旧批次存在 manifest/AI manifest，但默认 SQLite 没有对应 `input_batches`、素材和分析图；
- 旧提交链路没有保存足够的完整批次元数据，无法在重启时安全重建；
- AI 读取孤立 manifest 时必须 fail closed，不能把持久化不一致误报为“图片不匹配”或继续调用 provider。

## 实现修正

- 新增 `input-commit-journal/v1`，journal 只保存重建批次所需的元数据、digest 和暂存 token，不保存图片/PSD 字节；
- 输入提交顺序改为“manifest staging → journal → 不可取消 SQLite 提交屏障 → manifest commit → 三方核验”；
- 重启可由 journal + committed manifest 重建缺失的 SQLite 批次；
- SQLite 使用 `synchronous=FULL`，单 writer 生命周期受保护，安全退出执行 WAL checkpoint；
- SQLite 已提交但 manifest 提交失败时保留暂存证据，交给重启恢复；提交附近取消不会覆盖可能已提交的 ready 图；
- 孤立 manifest/hash 与缺失 SQLite 行报告为本地状态不一致；AI checkpoint/manifest 不一致时 provider 调用数为 0；
- 保持 24 张单请求上限、ready buffer 32、HTTP 并发 8、副本准备最多 2 路、预算/未知结果/源文件只读边界不变。

## 2026-09-09 排序误判与恢复包真实批次复核补充

### 排序误判修复

旧批次在提交后的三方核验阶段仍可能被错误标为 `RecoveryRequired`：journal 按扫描顺序保存同款 `AssetIds`，SQLite 读取时按 `source_relative_path` 排序，Windows 大小写排序差异会让严格序列比较失败。`InputCommitJournalConsistency.StyleComparer` 现按稳定 Ordinal 顺序比较 `AssetIds`，明确把它视为素材集合而不是有序序列；新增 `CommittedBatchIgnoresAssetOrderChangedBySqliteCollation` 回归，使用 `a.png`/`B.png` 覆盖该差异。

### 模板包运行时兼容补充

真实导入恢复包时又发现运行时 Schema 会把当前 PSD 检查模型中的可选 `embeddedContentSha256`、`embeddedContentAvailable` 和 `pixelEvidence` 字段重新序列化，而 `template-package-v1` Schema 尚未声明这些字段，导致包在导入前被报为 `TPL_PACKAGE_INVALID`。Schema 已补为向后兼容的可选字段；新增带 `JsonSchemaContractValidator` 的 `RuntimeSchemaAcceptsCurrentPsdEvidenceProjectionAndLegacyNulls` 回归。该修正不改变旧包字段含义，也不放宽路径、哈希、层结构或来源文件安全门。
