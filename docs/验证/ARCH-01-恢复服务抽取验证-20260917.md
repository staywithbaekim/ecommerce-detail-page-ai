## 恢复与资源所有权

| 内容 | 抽取后归属 |
| --- | --- |
| 上下文缓存、创建门、后台关闭与等待 | 原工作流 |
| scheduler、admission/consumer 任务和取消源 | 原批次上下文及工作流 |
| scheduler 恢复锁与已尝试标记 | 每上下文独立的恢复服务 |
| checkpoint 恢复锁与已尝试标记 | 同一恢复服务，保持独立锁 |
| 两阶段共享恢复错误 | 恢复服务，只公开读取 |
| scheduler 内部队列/预算/未知结果恢复 | 原 scheduler 实现 |
| SQLite/manifest 恢复 | 既有 checkpoint 端口及 coordinator |

`BatchContext` 创建 `AiAnalysisRecoveryService(batch.BatchId, scheduler, checkpointPort)`，服务借用 scheduler，在原两道锁的释放位置释放服务；只释放自己的锁，不接管 scheduler 或后台任务。工作流仍在原位置持有 checkpoint 端口以创建上下文。

保留的行为：

- Start、Refresh 和 Control 仍依次调用 scheduler 恢复、批次 checkpoint 恢复。Start 保留恢复错误阻断；其他入口没有新增阻断。
- LockSelection、SelectSizeTableSource、AnalyzeSelectedAsset 和 PrepareRendering 仍只调用原有 scheduler 恢复；没有隐式增加 checkpoint 调用。
- 两阶段各自入锁，并在实际 I/O 前标记已尝试。入锁前取消传播且不消耗尝试；已进入 I/O 后取消或异常仍消耗尝试，同一上下文不重试。这是既有语义，不是新取消策略。
- 只捕获 `InvalidOperationException` 并保留其 Message；checkpoint 的 `RecoveryRequired` 使用 ReasonCode 覆盖共享错误，成功结果不清除先前错误。I/O/损坏/取消异常继续传播。
- checkpoint 未配置时原样直接返回，包括已取消令牌。两道锁不合并，不增加跨阶段同步。

原三段恢复/阻断方法及上下文中的两道锁、两项标记、错误属性已移除。公开构造函数和用例方法签名不变，后台 admission/consumer、重试规则、schema、migration、checkpoint/manifest 和 bridge 合同不变。
