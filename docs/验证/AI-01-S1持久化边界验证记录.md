# AI-01 S1 持久化边界验证记录

## 范围与基线

本记录覆盖 AI-01 S1 的领域状态/CAS、SQLite request ledger/session/cache/usage、`ai-analysis-state/v1` 文件 manifest，以及两者之间的业务 checkpoint 编排。本轮跨资源增量从主线治理头 `ea9b7225ae4e3e07672e363b8a388431bdd14e7f` 建立独立分支 `codex/ai-01-s1-orchestration`，父链包含已审查的持久化边界功能提交 `1b854dbc92177ed94ecfca22d8e091143eae9908`；不包含火山方舟 provider、Credential Manager、联网、队列/费用阈值、WPF、动态尺码或 Photoshop 批量渲染。

AI 文件协议实际使用：

- `staging/{stage-token}.json` 保存暂存 manifest；
- `staged.marker` 记录 stage token、目标 manifest 引用和 digest，重启后可据此重建精确的 staged record；
- `manifests/{stage-token}.json` 是不可变提交候选，`committed.marker` 最后原子切换到该版本；更新 marker 写入失败时，旧 committed 版本继续可读，新 stage 可在重启后继续提交；
- 当前协议没有单独的 `ready.marker`。marker、stage token、manifest reference、digest、manifest 内容、创建时间和列表语义均在读写时校验。

跨资源协议使用“批次全量 manifest + 多个款级 graph”，不是只含当前款的增量 manifest：

1. 先 stage 完整批次 manifest；
2. 在一个 SQLite v7 单 writer transaction 中 CAS 写入全部 request/session、可选 usage/cache 图，并写入 durable `Pending` checkpoint header/items journal；
3. 原子切换 `committed.marker`；
4. 最后用 checkpoint ID、stage token、manifest/payload digest 和 journal state CAS 将 journal 收口为 `Committed`。

usage/cache 按结果状态闭合且不被强制存在：失败、取消、`AiResultUnknown`、无缓存人工结果或供应商无可用计量时二者可为空；usage 可独立存在；cache 存在时 usage、request/result、model config 和时间必须闭合。新 checkpoint 的 `CreatedAt` 必须严格晚于同批次最新 committed 版本，且必须保留上一版全部历史 request/session graph；payload 完全相同也不能绕过 expected status/revision CAS。AI-S1 不提供 cache 删除命令，因此上一活动 checkpoint 的 usage/cache 引用也单调保留；将来若需依法失效或清理，必须由 AI-S3 显式协议在核对活动引用后执行，不能靠 checkpoint 覆盖静默移除。

历史各自边界的 reviewed diff 最终提交为 `1b854dbc92177ed94ecfca22d8e091143eae9908`，已 fast-forward 合并 `codex/desktop-foundation-01`。本轮跨资源增量已在独立分支完成 build、聚焦与完整 solution 验证，仍待主任务独立 reviewed diff 和 fast-forward 合并；因此不能据此宣称 AI-01、真实 AI 或后续阶段通过。


当前分支聚焦结果：Infrastructure 90/90。随后完整 solution 重新执行结果为 211/211（Contracts 30、Domain 40、Application 41、Infrastructure 90、Architecture 5、UI 5），build 0 警告/0 错误；历史 184/184 不覆盖本轮新增 checkpoint 测试。

覆盖证据包括：

- 同一 request fingerprint 幂等、规范初始 ledger（Queued/null/时间一致）、SHA-256 指纹和结果引用状态闭合；
- request 状态受控 CAS，Validated→ManualReview/PlanClosed 保留既有结果引用；终态回退、跨阶段跳跃和旧状态覆盖均拒绝；
- session selection revision CAS：同状态递增 revision 的第二次换图可保存，同 revision 偷换、允许集合替换、PlanClosed/TerminalError 回退均拒绝；
- usage/cache 只接受非负计量、费用币种配对、相对 owned reference；usage 必须关联 ledger，cache 必须关联 usage、model config、时间和 ledger result；同 key 不一致 payload 结构化拒绝；
- decimal 费用使用稳定文本保存；usage 时间不得早于 request ledger，损坏 ledger/cache/usage 的时间、enum、decimal、布尔值和引用在读取时映射为 `InvalidDataException`；
- manifest staged record 真实重启重建、提交幂等、A/B 更新隔离、旧 committed 保持可读、marker 写失败后继续提交、伪造 token/reference/digest/列表和非法时间拒绝，以及应用自有 stage/旧 manifest 安全清理。
- full-batch 多 graph 的 request/session/usage/cache/manifest 精确闭合；上一 committed 版本的历史 graph 不得被新版本遗漏，较旧或同时间版本不得覆盖较新 manifest；相同 payload 仍严格核对 expected status/revision。
- 合法可选图：`AiResultUnknown`、`TerminalError`、`Cancelled` 和成功但无计量/缓存均可提交；usage 可无 cache；cache 无 usage、result/model/time 不闭合均拒绝。
- 跨资源恢复矩阵：DB pending + staged、DB pending + committed、staged 无 DB journal、DB committed 但 manifest 缺失、SQLite journal 写失败、marker 写入前失败、marker 已写后抛错、SQLite prepare/finalize 已提交后抛错、重复命令和真实 store/coordinator 重建；direct Commit 在 committed manifest 无 journal 或 journal/manifest 缺失不符时拒绝并保留旧 marker。
- SQLite v6→v7 正向迁移保留 sentinel；v7 注入失败时事务回滚到 v6，checkpoint 表不残留；损坏 journal 稳定映射为 `InvalidDataException`/`RecoveryRequired`。
