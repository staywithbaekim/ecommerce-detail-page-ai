# AI-01 S3 有界调度与费用门验证记录

## 范围

本记录覆盖 AI-S3 的第一轮应用层实现：有界去重工作缓冲、按款联合理解与调用方确认资产的精细分析入口、内容型 SHA-256 cache key、显式 cache 命中/失效、有限重试、AiResultUnknown 不重试、usage 计量累积以及由调用方提供价格/预算的告警与硬停止。实现通过供应商无关 IAiAnalysisWorkBuffer、IAiServicePort 和现有 IAiAnalysisStore 工作，不复制 INPUT-01 的 BatchDraft、扫描状态或 asset-manifest/v1。

本轮同时补齐了调度器最小持久化边界：SQLite v8 `ai_analysis_scheduler_state` 保存待处理 work item 的结构化请求投影、预算计数/估算费用和更新时间；请求/资产/分析副本引用均经过 ID、digest 和应用自有相对引用校验。队列入队、重试替换、provider 用量观察和终态清理都更新快照；重启只重新排入 ledger 仍为 `Queued`/`RetryableError` 的工作，`Uploading`/`Analysing` 保留为未决恢复证据而不猜成功或自动重试。

本轮新增 AI-S1/S3 跨资源 checkpoint 闭合：`ai-analysis-state/v1` manifest 可携带 scheduler digest；SQLite v9 在同一事务内写入 scheduler 快照、full-batch ledger/session/usage/cache 图和 durable pending journal。journal 保存 scheduler state key/digest/结构化快照，恢复时重新校验快照与数据库行、pending work 对应 graph、Queued/Retryable 状态不得遗漏、历史引用不得删除。manifest marker 提交前后未知、SQLite 事务失败、重启后的 pending/staged 或 pending/committed 均沿用既有 RecoveryRequired/读回确认语义，不把 provider、Key、原始响应、图片字节或绝对路径写入 checkpoint。

本轮增量补充批次级入口与控制状态：`AiAnalysisScheduler.EnqueueBatchAsync` 直接消费已完成 INPUT-01 扫描的 `BatchDraft`、模板快照和 `asset-manifest/v1` 元数据，按稳定款式顺序为每款建立第一层 `ProductJointUnderstanding` 请求；不重新扫描目录、不复制 `BatchDraft`/manifest。调度状态新增 `Running`、`PauseRequested`、`Paused`、`WaitingForNetwork`、`Cancelled`，并持久化控制原因。暂停只在请求边界阻止 provider 调用，恢复重新排入仍为 `Queued`/`RetryableError` 的工作；取消只推进未开始款，已进入 provider 的未知结果保持原有审计状态；网络等待是显式本地控制，不把超时/断网的供应商未知结果猜成成功。SQLite v10 增加控制列，scheduler digest 与 checkpoint 一并覆盖控制字段。

覆盖：

- 队列容量上限、活动 work item 去重和溢出拒绝；
- cache key 由排序后的资产 hash、分析类型、模型/Prompt/响应 Schema/压缩版本和 requirements digest 计算，稳定为 sha256: + 64 位小写十六进制；
- 款内联合理解先入队；精细主体/尺码分析只接受调用方确认且属于首层请求的资产，不会上传未选候选；
- provider 成功记录 usage、结果引用、Validated 状态和 cache reference；等价请求命中 cache 不重复调用 provider；
- RetryableError 在上限内回队列，AiResultUnknown 进入未知状态且不自动重试；
- 请求数/输入输出计量/估算费用达到策略硬停止时阻断后续 provider 调用；告警与停止使用调用方显式价格，不脑补火山方舟账单金额；
- cache 失效为显式操作，删除前复核引用闭合。
- 调度快照在 SQLite v8 中可跨 `SqliteDesktopStore` 重启恢复；损坏 JSON 映射为 `InvalidDataException`，版本迁移保留既有 v5/v6 sentinel。
- 调度快照与 full-batch checkpoint 在 SQLite v9 同一事务中写入并由 manifest digest 闭合；checkpoint 重启恢复会复核 scheduler 快照，拒绝遗漏 Queued/Retryable、digest 不符和 scheduler 引用悬空。
- SQLite v10 的控制状态/原因列可跨 `SqliteDesktopStore` 重启恢复；批次生产者测试证明 ready 批次按款式顺序建立一请求/款的首层联合理解工作项，暂停/恢复/取消测试证明 provider 不会在控制边界被额外调用；`CancelRequested` 重启会完成队列任务的明确取消且不重新入队；provider 异常保守映射为 `AiResultUnknown`，指定批次取消不会误伤同调度器中的其他批次；新 checkpoint 拒绝调度预算回退、控制状态回退和待处理项遗漏。

测试中的 provider 为明确标注的离线 sequence double，仅验证状态和边界；不代表真实 AI 语义准确率、费用或延迟。真实方舟结构化探测证据见 docs/验证/AI-01-S2火山方舟受控探测验证记录.md。

## 本轮 reviewed diff 修正（2026-08-30）

- 批次入口现在可在有副本生产器时完成 `ScanReady BatchDraft -> IAiAnalysisCopyPreparer -> AiAnalysisRequestV1` 投影；每个 asset 的分析副本 digest/长度/MIME/压缩 profile/lease 进入请求合同，源相对路径仅在临时生产调用中使用。
- provider adapter 不再拥有正式副本的清理权；租约 token 集合持久化在应用自有 sidecar，scheduler 在入队/恢复时取得租约，在重试、暂停和第一层转精细分析时保留或转移所有权，共享引用按 token 独立释放。成功终结、取消和不可恢复失败只释放对应请求的租约；清理失败保留可恢复错误，不触碰源文件。
- scheduler 成功路径先通过 `IAiAnalysisResultStore` 原子保存结果，再写 usage/ledger/session/cache；结果缺失、损坏或写入失败不能标记 `Validated`。cache 命中在启用结果存储时必须读回真实结果。
- adapter 资源上限修正为副本 metadata 预检、Content-Length 提前拒绝、chunked 受限读取和统一超时 token；离线测试覆盖正式请求不发送和响应边界。

第二轮 reviewed diff 将 scheduler 正式业务路径接入现有跨 SQLite/manifest checkpoint：入队、重试、暂停/恢复、取消、usage/cache/结果终结均以批次全量历史 graph 与 scheduler snapshot 构造 checkpoint，SQLite transaction 和 manifest marker 继续沿用 S1 的 pending journal/RecoveryRequired 协议。cache hit 必须从 `IAiAnalysisResultStore` 读回并校验 Schema、源 request、model 和 result reference；缺失、损坏或不匹配显式返回 `AI_CACHE_RESULT_INVALID`，不得推进 `Validated`。正式 copy/checkpoint 流程缺少 result store 时返回 `AI_RESULT_STORE_REQUIRED`。真实 `SqliteDesktopStore` + manifest 集成测试证明提交后无 pending work、重启可恢复；同时修正费用 decimal 科学计数法文本的无损读取。

这些修正不新增真实联网调用。当前历史真实探测仅用于证明服务可访问和最小结构化返回，不足以冻结 S2 的压缩/批量/并发/重试/费用参数，因此 S3 退出门仍未满足。B-02/B-03/WPF 属于 S4，真实金标属于 S5，本记录不将其列为 S3 内部交付。

## 第三轮 P0 补正（2026-08-30）

- checkpoint 启用时，cache-hit 的最终 `Validated`、既有 cache 原始 usage 与 cache reference 通过同一个 full-batch graph 提交；不再调用直接写 store 的 cache usage/完成方法。注入最终 checkpoint 失败时 ledger/session 保持 `Analysing`，usage 数量不增加，不能留下部分成功。
- 每次 `PrepareAsync` 返回的随机 lease 只有在转换为稳定 work lease 后才算被 scheduler 接管。重复批次、queue-active、pending duplicate、已取消、既有请求不接管、混批拒绝及 Enqueue 异常均释放本次 prepared lease；多素材准备在第 N 项失败时回收前 N-1 项。
- checkpoint scheduler 实例严格绑定一个 batch scope；第二批在修改 history/store 前被拒绝并保留第一批队列。使用不同 state key 的独立 scheduler 可分别提交各自 batch，命令不会混合 graph。
